# Developing PowerPane

This guide covers building, testing, and releasing Explorer PowerPane. The README describes what PowerPane does and how its parts fit together. This file covers how to work on it safely.

## Requirements

- Windows 10 or 11, x64.
- Visual Studio or the Visual Studio Build Tools, 2019 or later, with MSBuild and the .NET desktop build tools.
- The .NET 8 SDK, which runs the unit tests.
- The .NET Framework 4.8 targeting pack is optional. `scripts/build.ps1` downloads Microsoft's signed reference-assembly package when the pack is missing.
- Inno Setup 6, which `scripts/package.ps1` uses to build the installer. CI pins 6.7.1. Without it, pass `-NoInstaller` to package only the zip.

## Build

```powershell
pwsh -File scripts/build.ps1                      # Release, x64
pwsh -File scripts/build.ps1 -Configuration Debug
```

The script finds MSBuild through `vswhere`, builds `PowerPane/PowerPane.csproj`, and prints the output path, version, and SHA-256. The exe lands in `PowerPane\bin\x64\<Configuration>\PowerPane.exe`.

The script builds the app project, not `PowerPane.sln`. Visual Studio 2019's MSBuild cannot load the SDK-style test project, so the test project stays out of the solution. With Visual Studio 2022 you may still open the solution as usual.

## Test

```powershell
pwsh -File scripts/test.ps1            # builds, then runs the tests
pwsh -File scripts/test.ps1 -NoBuild   # tests only
```

The tests live in `tests/PowerPane.Tests`, an SDK-style `net48` NUnit project. It references the built `PowerPane.exe` through a `HintPath` rather than a project reference, because the .NET SDK cannot build the legacy WPF project. Build the app first with the same configuration.

`[assembly: InternalsVisibleTo("PowerPane.Tests")]` lets tests reach `internal` code. Logic worth testing should be `internal`, not `private`.

### Rules for tests

- A test must only touch a temporary directory that it creates and deletes. `TempDir.cs` provides one.
- Never use `SettingsStore`'s default constructor in a test. It reads and writes the real `%APPDATA%\PowerPane`. Use `new SettingsStore(tempDir)`, and point `groupsPath` inside the temporary directory too.
- Never call `GroupStore.Recycle` or `DeleteTab` on real folders. Either would put test folders in the developer's Recycle Bin.
- Never start `PowerPane.exe` from a test, and never show a window or dialog.
- Keep expected failures out of the log. Before `Log.Init` runs, `Log` writes to `powerpane.log` in the system temp folder, which is outside the test's own directory. `WorkLane` and `WinEventHub` take an `onError` handler for this reason. A test that makes either fail on purpose passes its own handler.
- Prefer pulling a decision out into a pure `internal static` method and testing that. `DialogPaneWatcher.ResolveMode` is an example.

## CI

`.github/workflows/ci.yml` runs on every push to `main` and on every pull request. It calls the same scripts on `windows-latest`: the rules check, build, test, and `scripts/package.ps1`, which makes the installer, the release zip, `SHA256SUMS.txt`, and the release notes. `package.ps1` fails when the zip does not hold exactly `PowerPane.exe`, `PowerPane.exe.config`, `LICENSE`, and `THIRD-PARTY-NOTICES.txt`, or when the notices file has lost one of its copyright lines (#278). It keeps that packaged output as a workflow artifact. Packaging runs on every build so that a broken release step fails a pull request rather than a tag. It also fails when the version in `AssemblyInfo.cs` has no release document and no changelog section yet. CI cannot exercise the app itself: Explorer windows, window hooks, and file dialogs need a real desktop.

`scripts/check-rules.ps1` runs first, in CI and at the start of `scripts/test.ps1`. It checks the rules that still compile and pass every test when broken:

- Every `.cs` file under `PowerPane/` is listed in `PowerPane/PowerPane.csproj`.
- No file other than `WinEventHook.cs` and `NativeMethods.cs` calls `SetWinEventHook`.
- No tracked text file holds a raw private-use character (U+E000 to U+F8FF). That covers code, XAML, scripts, and documentation, chosen by file extension so images and icons are skipped. Icon glyphs are written as `"\uE713"` in C# and `&#xE713;` in XAML, because some editors and tools drop the raw characters without a trace. One such edit once emptied every icon on the Settings Pane page.
- No test uses `SettingsStore`'s default constructor.
- `packaging/Install.ps1` and `packaging/Uninstall.ps1`, which nothing runs in CI, still match the setup program. Neither may stop PowerPane with `Stop-Process` or `taskkill`, and both must pass `--exit`. `Install.ps1` must find every file before it closes the app and must install the same files as `Installer.iss`'s `[Files]` section. `Uninstall.ps1` must close the app before it removes anything, and must remove the Start menu shortcut named by `ShortcutRepair.LinkName`, which `Installer.iss` must also use. The scripts are read with the PowerShell parser, so comments do not count.

A failure lists every file and line that breaks a rule.

`.github/workflows/release.yml` runs when a `v*` tag is pushed. It is described under [Releasing](#releasing).

`main` is protected. A change reaches it only through a pull request whose `build-and-test` check passed, and the rule applies to administrators too. No approving review is required, because GitHub does not let authors approve their own pull requests. Force-pushes to `main` and deleting `main` are blocked, and merged branches are deleted automatically. The rule lives in the repository's Settings, under Branches.

## Running a development build

Only one copy of PowerPane runs at a time, because a single-instance mutex guards it. A development build therefore replaces the installed copy while it runs.

`scripts/dev-run.ps1` does the steps below for you. It builds, backs up your settings to `%LOCALAPPDATA%\PowerPane-dev-backups`, closes the running copy with `--exit`, and runs the build. When you close the build from its tray icon, it starts the installed copy again. It waits through a watchdog relaunch, so a crash during the test does not bring the installed copy back early. If you stop the script before then, run it with `-RestoreInstalled`.

```powershell
pwsh -File scripts/dev-run.ps1              # build Release, then run it
pwsh -File scripts/dev-run.ps1 -NoBuild     # run the existing build
pwsh -File scripts/dev-run.ps1 -RestoreInstalled
```

A build run from `bin\` lasts until you sign out. Windows starts the installed copy at sign-in, because the Run key points at `%LOCALAPPDATA%\PowerPane`.

The manual steps, if you prefer them:

1. Back up `%APPDATA%\PowerPane`. A development build reads and writes the same settings and groups.
2. Close the installed copy: `& "$env:LOCALAPPDATA\PowerPane\PowerPane.exe" --exit`. Do not kill the process. A kill skips the layout restore, and the watchdog process restarts the app.
3. Run `PowerPane\bin\x64\Release\PowerPane.exe`.
4. When finished, close it with `--exit` and start the installed copy again. `ShortcutRepair` points the Start menu shortcut at whichever copy ran last, so restarting the installed copy repairs it.

Windows Sandbox makes a safe test bed for UI checks. It is a disposable desktop with no personal files, where scripted clicks cannot disturb your own windows.

## Recording a performance trace

PowerPane writes trace events through an `EventSource` named `PowerPane`, in `PowerPane/Services/PerfTrace.cs` (#219). The events mark the start and end of background lane jobs, pane and group rebuilds, and cross-process calls into Explorer windows and file dialogs. A trace records them on the same timeline as Explorer's threads, CPU use, and waits, which the text log cannot show. That makes a trace the tool for a stall whose cause the log does not explain, such as #53.

The events cost almost nothing until a trace asks for them, and nothing is sent anywhere. Payloads carry kinds, counts, and durations, never a folder or file name, so a trace can be shared to ask for help. A trace also holds Windows' own data, such as other programs' names and window titles, so look at it before sharing it.

Windows Performance Recorder is built into Windows. It needs an administrator prompt.

```powershell
wpr -start scripts\trace\PowerPane.wprp -filemode
# reproduce the stall, then:
wpr -stop $env:USERPROFILE\Desktop\powerpane-stall.etl
```

Open the `.etl` file in Windows Performance Analyzer. PowerPane's events appear under Generic Events, provider `PowerPane`. The profile names the provider by its GUID, `fc252778-1bf6-528a-95dd-a5d921cdc8e5`, because WPR does not take an `EventSource` name. A test fails if the provider's name and the GUID drift apart.

PerfView takes the name directly: `PerfView /OnlyProviders=*PowerPane collect`.

## Code conventions

- **C# 7.3 and .NET Framework 4.8 only.** That rules out switch expressions, `is not` patterns, nullable reference types, `using` declarations, ranges, records, and target-typed `new()`.
- **The app project lists every file.** A new `.cs` file needs a `<Compile Include="..." />` line in `PowerPane/PowerPane.csproj`, or it will not compile.
- **Comments explain why.** The codebase documents the reason behind each non-obvious choice, often a past bug. Keep that style.
- **One change per commit.** Each fix should be one commit, so it can be reviewed, reverted, or cherry-picked on its own.
- **No personal data.** Use invented paths such as `C:\Demo\Projects` in tests, comments, issues, and commit messages.
- **The pane matches Explorer's own color by default.** A Settings pane color other than Default (the swatches on the Pane page) is the person's own opt-in; never default a theme, profile, or release to a color choice they didn't make.

## Traps in the code

| Area | What to know |
|---|---|
| Inside mode | `ExplorerWindow` hosts the pane as a child window of Explorer's `CabinetWClass` and shifts the tab content right with `SetWindowPos`. |
| Window resizes | Explorer puts every tab back at x=0 and full width on every resize, a programmatic `SetWindowPos` included, and PowerPane shifts it back within milliseconds. During a border drag that correction is visible as flicker, so `ExplorerWatcher` leaves the window to Explorer between `EVENT_SYSTEM_MOVESIZESTART` and `EVENT_SYSTEM_MOVESIZEEND` and Explorer's tab sits at the left edge, behind the inside pane, until release. `ExplorerWindow.HidesForDrag` hides the inside pane once the drag has changed the client size, and only while the top tab shows a visible `SysTreeView32` under `NamespaceTreeControl`. That condition is read live, because a window applies the navigation-pane setting only when it opens another folder, and Explorer drops the tree on its own in a very narrow window. #102 hid the pane for every resize, which showed an empty strip with Explorer's navigation pane off. 4.1.0 kept it up for every resize, which covered Explorer's tree for the whole drag. A title-bar move or a click on the border never changes the size, so it never hides the pane. `EndDrag` reapplies the split and then shows the pane, even when the layout pass returns early. A beside pane hides for a title-bar move and for a resize that moves the window's left, top, or bottom edge; a right-edge drag keeps it up; see #147 and #235. The one-second sweep releases a window whose end event is lost once Explorer's thread leaves its move/size loop (`ExplorerWatcher.DragEndLost`), and a 30-second cap is the last resort. See #99 and #102. |
| Windows 11 tabs | Each Explorer tab has its own `ShellTabWindowClass` child. All of them stay visible, with the active one on top, and Explorer resets every tab to full width when a tab opens or closes. `ExplorerWindow` therefore walks all of them live on every layout pass. Never cache one tab's handle, because tabs open and close while the window lives. See #4. |
| Keyboard focus | The embedded pane is a child of another process's window, so it cannot take keyboard focus normally. Typing happens in separate top-level windows such as `TextPrompt`. See lso2/QuickPane#4. |
| File dialogs | `DialogPaneWatcher` attaches panes to standard `#32770` dialogs, inside or beside. A dialog that moves its controls back over the pane at an unchanged width is handed to beside, and its app joins the beside list for the rest of the session only after `DialogPaneWatcher.FightsBeforeBeside` (two) separate dialogs have done so: one unexplained fight used to put every later dialog from that app beside while other apps kept the pane inside. The glitch line names the last recorded action and its age, read before `Restore` resets it. A width change never counts against the app. The common Save dialog applies its remembered size just after the pane attaches, so `DialogInsidePane` fits the pane inside the width the dialog chose. Never widen the dialog at that point: the shell records the size before the restore on hide runs, so each Save As would reopen one pane wider than the last. A user's border drag hides the pane until release. See #103. A drag on the size grip starts further in than `ResizeBorder`'s band, and a keyboard resize has no press at all, so `DialogInsidePane.UserResizeMissed` starts the same handling at the first size change seen while the dialog's thread is in its move/size loop. The common Save dialog's own resize just after attach runs outside any loop, so it still takes the fit-inside path. A drag whose end event is lost ends once that loop has ended, or at the 30-second cap. See #234. At attach, a dialog with room for at least `MinContentPx` beside the pane shares its own width (`DialogInsidePane.WantsSharedWidth` and `ShareWidth`) and is widened only when it is too narrow: a Select Folder dialog applies its remembered size before the pane attaches, so widening it at attach made it reopen one pane wider every time. A Select Folder dialog also builds its address bar's path box only when the bar is first activated, where Save As builds it at once, hidden. `DialogNavigator.OpenAddressEdit` posts a click to the breadcrumb toolbar's empty end to build it. A dialog with an address bar but no file type list never gets the File name box route, because in a Select Folder dialog that box chooses the folder and closes the dialog. PowerPane's own pickers get no pane: the shared hook skips this process, so a pane on them never heard of a move or resize, and only the one-second sweep reached it. `DialogPaneWatcher` treats this process's dialogs as final misses, and `PickerPlaces` lists the pins in each picker's navigation pane instead, through `IFileDialog::AddPlace` or WPF's `FileDialog.CustomPlaces`. A new picker opened by PowerPane should call `PickerPlaces.AddTo` or go through `FolderPicker`. See #231. A beside pane is its own top-level window, so it only moves after a `LOCATIONCHANGE` notification reaches us, which trails a fast drag of the dialog (title bar included, not just the border) by a frame or more. `FollowerPane.BeginDrag`/`EndDrag`, driven by `OnMoveSize` in both `DialogPaneWatcher` and `ExplorerFollowerWatcher`, hide the beside pane once the window's left, top, or bottom edge leaves where it was when the move loop began (`FollowerPane.HideForMove`; the right edge is ignored, because the pane depends only on the others, #235), and place it once from the final rect on `MOVESIZEEND`, so no frame shows it away from the window's edge. It does not hide on `MOVESIZESTART` itself, because a plain title-bar click enters the same loop and hiding then made the pane blink. See #147. |
| Folder picker | WinForms `FolderBrowserDialog` on .NET Framework 4.8 is the legacy tree dialog. Use `UI/FolderPicker.cs`, which wraps the modern `IFileOpenDialog`. |
| Pin row menus | A pinned row's menu is built on open by `LazyContextMenu`, because one menu per row per pane cost about 200 KB each and multiplied by pins and windows. WPF only opens a menu for an element that already has one, so `row.ContextMenu` is never null: it holds a shared empty placeholder until the menu opens. Do not mark `ContextMenuOpening` handled, because that skips the closing event that clears `SidebarControl.SuppressAutoHide`. |
| Row clicks | A click on a folder or file row runs the action chosen for its gesture in Settings (#269). Every such row goes through `RowClick`: `RowClick.Track` wires the mouse events, and `RowClick.Run` reads `ClickActions.Resolve` at click time and carries out the outcome, so a Settings change needs no pane rebuild. A row that handles its own click skips every gesture choice; the Codex review of #269 found that the App Folders rows, built from `FolderItem`, did this and ignored the settings. A release acts only when it completes a press begun on the same row (`RowPress`), because a click can now run a quick action or a custom command, and a press in blank space dragged over a row used to act on release. `ClickActions` holds every decision as pure code with tests: the gesture a button and modifiers make (Alt and the Windows key are ignored, as a left click always ignored them), the defaults that keep the old clicks, what an action means on a missing folder or inside a dialog, and when a quick action may run, by the same rules as a pinned row's Quick actions submenu. Open in new tab is not offered: Explorer has no supported call for it, and sending Ctrl+T while the user holds Shift becomes Ctrl+Shift+T, which reopens a closed tab. |
| Window icons | Take an icon for a window or an image from `AppIconFrames`, never from `Icon.ExtractAssociatedIcon`. That call returns only the 32 px frame, so the Settings title bar drew it shrunk to 16 px and blurred (#271). `AppIconFrames.At` picks the smallest frame of `powerpane.ico` that is at least the target size at the current display scale, and the Settings window asks again when the scale changes. `AppIconFrames.ForWindow` gives the window the whole decoded icon, so Windows picks its own sizes for the taskbar and Alt+Tab. The decoder is built inside a `try` at call time, never in a static field, because a pack URI throws outside a running WPF application, as in the tests. |
| Settings title row | The title row is 48 px tall, but the caption buttons that `WindowChrome` draws are about 30 px tall at the top, so centring the icon and title on the row left them about 9 px below the buttons' glyphs (#276). `SettingsWindow.UpdateTitleBand` centres them on the buttons instead, using `DWMWA_CAPTION_BUTTON_BOUNDS`. DWM gives those bounds from the top of the visible frame, which a maximized window places 8 px below its own rectangle at 100 % scale, so the code adds that gap. The same gap is the maximized margin: `SystemParameters.WindowResizeBorderThickness` reports only 4 px of it and leaves out the padded border, so `UpdateMaximizedMargin` measures the window rectangle against `DWMWA_EXTENDED_FRAME_BOUNDS`. The log in `%APPDATA%\PowerPane\Logs` records each band as "caption buttons at y ...": at 100 % scale a normal window reads "y 0..30 px, frame offset 0 px" and a maximized one "frame offset 8 px, ... root top 8", both with a title band of top 0 and height 30. A band of height 32 means DWM gave no bounds and the fallback applied. The icon sits 16 px from the left and the title 16 px after it, as Microsoft's title bar guidance says. |
| Deleting | `GroupStore.Recycle` sends a folder to the Recycle Bin. Use it, never `Directory.Delete`, for anything that holds a user's pins. |
| Settings structure | `PowerPane/UI/Settings/` holds `SettingsWindow.cs` (the shell: navigation pane, search, breadcrumb, Mica), `SettingsCards.cs` (shared, theme-live card builders), `SettingsSearch.cs` (the search index, built with no `SettingsStore` and no `GroupStore`), and `Pages/*.cs`, one file per page. Every page implements `SettingsPage` (`Id`, `Title`, `Glyph`, an optional `SearchEntries`, and `Build(SettingsPageContext)`). A page's constructor takes no arguments, because the search index is built once before any page opens. `Build` must do no disk, network, or COM work itself; post that through `WorkQueue` first, as the rest of the app does. Every control sets `AutomationProperties.Name`, so screen readers and UI-test tools can reach it. `SettingsPageBuildTests` builds every page from `SettingsWindow.BuildPages()` against a fake `ISettingsShell` and fails on any unnamed control, so a new page is tested without extra work. If a page's `Build` starts background work that would reach the network or the real disk, give it a seam the test can replace, as `AboutPage.CheckForUpdates` and `SshPage.SetInstallState` do. See #90, #96, and #120. |
| Fluent styles stay window-scoped | `PowerPane/Themes/Fluent/` is a port of Microsoft's WPF Fluent theme (see its `NOTICE.md`). `FluentThemeService` merges it into the Settings window's own `Resources` only, and must never merge a Fluent dictionary into `Application.Current.Resources`: every pane inside Explorer reads that level, so a style merged there would restyle the pane too. `FluentThemeServiceTests.AppliedDictionaries_NeverReachApplicationLevelResources` checks this holds. See #89. |
| Updating the Fluent port | To pick up a newer `dotnet/wpf` commit, read `PowerPane/Themes/Fluent/NOTICE.md` first: it names the ported folders and why `ListView`, `DataGrid`, and `Window.xaml` were left out. Then read the #89 commit message for every change PowerPane made to build the port on C# 7.3 and .NET Framework 4.8, such as the `xmlns:system` fix, `StaticResource` references changed to `DynamicResource`, the one C# 9 pattern rewritten, and the placeholder `SystemAccentColor*` keys `FluentThemeService` overwrites at load time. Re-apply the same changes to the new source, update the source commit in `NOTICE.md` and in `THIRD-PARTY-NOTICES.txt` at the repository root, which ships beside the exe because compiled XAML keeps none of the ported files' copyright comments (#278), and run `FluentThemeServiceTests` plus a sandbox visit to every page before committing. |
| Versions | `UpdateService.Current` reads the assembly version. `UpdateService.Display` spells any version the way its tag does, with four parts when the fourth is not zero. `UpdateService.IsNewer` compares a tag with the running program, counting a missing part as 0, because a Semantic Versioning tag (v4.1.0) has three parts and the program's version (4.1.0.0) always has four. Use it, never `Version.ToString(3)`, which drops a fork build's fourth part. |
| Update check | `UpdateService` asks GitHub for this repository's `releases/latest`, which skips drafts and pre-releases. A 404 means no published release yet and reads as "Up to date". The About page marks a version as noticed only once the result is on screen, so leaving the page during a request does not use up the notice. `UpdateNotifier` runs the same check at most once a day, unless `updateCheckOff` is set. It records the attempt before the request, so an offline machine waits a day instead of retrying hourly, and `updateNoticeVersion` keeps the notice to one per version. The README's privacy section states this schedule, so change the two together. The About page's download button takes the release's first `.exe` file. A release carries the installer under two names, `PowerPane-<version>-x64-setup.exe` and `PowerPane-x64-setup.exe`, so either may be the one chosen, and the two must stay the same file. `scripts/package.ps1` makes the second as a copy of the first. If PowerPane is ever packaged as MSIX, the Store updates the app, and the notice should be hidden for that install. See #176. Its timer runs at Normal priority, because a `DispatcherTimer` defaults to Background, which WPF holds back while input is pending. One Sandbox run saw the check wait until the cursor moved, and five later runs could not repeat it, so the cause is inferred. See #199. Other default-priority timers, such as `ExplorerWatcher`'s sweep and `RecentTracker`'s poll, have not been measured for this. |
| Slow work and threads | In inside mode the UI thread shares Explorer's input queue, so one blocking call on it stalls Explorer too. Disk, network, and cross-process COM work goes to `WorkQueue`, which has two background STA lanes. `WorkQueue.PostNavigation` is only for driving an Explorer window or a file dialog to a folder the user clicked. Everything else uses `WorkQueue.Post`. A click used to wait behind Recent polls, copies, and network probes on a single lane. See #38. |
| Checks the user waits for | When the UI must know an answer before it can continue, such as a picker's start folder, use `PathStatus.FolderExistsWithin`. It gives up after `InteractiveProbeMs` and reports a timeout separately from "missing". A bare `Directory.Exists` on an unreachable share waits for the network timeout. See #41. |
| Probe results the pane shows | `PathStatus` answers from a cache and probes in the background. Its `Changed` event rebuilds the Groups and Recent sections, so it fires only when a probe changes what a row shows (alive or gone, file or folder), or on a first probe that a `ConfirmedAlive` reader waits on, such as restoring an expanded subtree. A first probe that only confirms the optimistic answer raises `Probed` instead, which rebuilds nothing: raising `Changed` for it made an expanded pin on a share re-list its children once per child probe. `PathStatus.ProbeChangesRows` holds the rule. A value copied out of the cache goes stale when a later probe disagrees, so the pane reads it again as it builds: `GroupStore.RefreshLiveness` sets each pin's `Exists` and `IsFile` with `PathStatus.TryGetCached`. For a path the cache has no entry for, it starts the entry from what the row shows, not from the optimistic answer, and probes it. The probe is then compared with what is on screen: a broken pin evicted from the cache still comes back with its share, and a working set larger than the cache settles, because a probe that agrees with the row starts no rebuild. `ConfirmedAlive` creates its entry before it records that it waits, so a saved expansion never waits on nothing. See #136. Known limit: past 4,096 distinct pins drawn at once, the cache can evict an entry before its probe returns, and `Probe` drops a result whose entry is gone, so such a pin can stay wrong until the next scan; a saved expansion there can also keep rebuilding. Fixing either means tracking waiting rows apart from the result cache. A slow-volume icon waits for its path's first probe: `IconHelper` parks the extraction, keeps its rows registered, and hands it back to the drain on `Probed`, because rows such as This PC's network drives are never rebuilt by a probe. Read the probe with `PathStatus.State`, never `ConfirmedAlive` and a separate "probed" check, because a probe can land between two reads. The wait is safe only because probes and the icon drain share the one general worker. See #139. |
| Window event hooks | Create hooks with `WinEventHook`, never with `SetWinEventHook` directly. `WinEventHub` shares one native hook among every `WinEventHook` for the same event range on the same thread, so each event crosses processes once. Handlers run on the UI thread for events from the whole desktop. Reject unrelated events in the first line. See #43. Dispose a hook on the thread that created it: Windows removes a hook only there, and `WinEventHub` logs a detach from another thread. See #73. |
| Recent tracking | `RecentTracker` queries Explorer through COM when a window is activated. Its 2-second poll queries only when the front window, its front tab, or its title changed, or every 30 seconds otherwise. Anything that makes the poll query more often multiplies cross-process traffic. See #39. The title shows only the folder's own name, so a move from `C:\Demo\Alpha\Reports` to `C:\Demo\Beta\Reports` changes nothing the poll compares, and a visit that ends within 30 seconds is not recorded. This is an accepted trade-off. A navigation-complete signal from Explorer would remove it. See #74. |
| Pin sort modes | A tab's sort mode lives in a `.pane-sort` marker file inside the tab folder, holding `name` or `recent`; no file, or an unknown value, is Manual. A settings key was rejected because a tab has no stable identity: tab folders are renamed on every tab move and rename, and the marker travels with the folder through moves, merges, and profile copies. `GroupStore.LoadPins` applies the sort at scan time through `PinSorter.Order` and never rewrites the `NNN_` prefixes, so the Explorer right-click verb, which runs in another process, needs no change, and turning keep-sorted off loses nothing. `ReorderPins` deletes the marker after it writes an order, which is how a drag within a tab, Move up, and Move down return a tab to Manual. A pin inserted at a drop line (`AddPinAtIndex`, `MovePinToTabAt`) is placed in the order shown on screen and also clears the marker; a drop that names no position (`AddPins`, `MovePinToTab`) lands in its sorted place and keeps it. The quick switcher and the file-dialog places read `PinnedTab.Items`, so they follow the sort. The choice of a marker over a settings key is recorded in [decision 0001](internal/decisions/0001-tab-sort-mode-in-a-marker-file.md). A pin pinned to top (#301) carries `!` after its number, as in `003!_Apollo.lnk`, and `PinSorter.Order` puts those pins first and applies the tab's mode to each part. Every writer of a pin's file name builds it with `GroupStore.PinStem` and reads it with `GroupStore.SplitPin`, so none drops the flag; a new writer must do the same. `NextPinOrder` counts flagged numbers, `MovePin` never crosses the band's edge, a drop line decides the flag through `PinSorter.PlaceAtLineInBands`, and `MovePinToTab` writes the pin unpinned. Groups and tabs keep the plain `Prefix` pattern. A rename by hand in Explorer that drops the `!` unpins the pin. The flag in the file name is recorded in [decision 0002](internal/decisions/0002-pin-to-top-flag-in-the-file-name.md). |
| Prompt placement and add menu | `TextPrompt` opens next to the control that asked for it. A caller reads the control's screen rectangle with `PromptAnchor.Capture` before anything can rebuild the pane, and `PromptPlacement.Compute` turns it into a position in device pixels, flipped above the control when there is no room below and clamped to that monitor's work area. Never use `CenterScreen` when an anchor exists, and never give the prompt an owner, because an owner in Explorer's process joins the two input queues. A control that is gone by then gives a null anchor, and the prompt centres. The "+" buttons, the group menu, and the tab menu build their Add entries through `GroupAddMenu.AddEntries`, with words from `AddMenuLabels`. A menu opened in code raises no `ContextMenuOpening`, so `GroupAddMenu.Open` sets `SidebarControl.SuppressAutoHide` itself and clears it when the menu closes. A menu header needs `AddMenuLabels.EscapeAccessKeys`, or WPF drops a name's underscore. A group is labelled with its tab names joined by " / " (`GroupStore.DisplayName`), because a multi-tab group's own name never shows in the pane; the choice lives in `AddMenuLabels.GroupLabel` alone. In inside mode the "+" is mouse-only, for the same reason as every pane control. See #243. Pane prompts take a `PromptPalette` built from the pane's brushes, snapshotted when `AnchoredPrompt.Ask` opens them (#254). The Settings prompts pass none and keep the registry colours and a bare `TextBox`. When a brush the palette needs is missing, or before `App.Theme` exists, the palette is null and the prompt reads the registry, so it never guesses the mode. |
| Profiles and groups | A profile switch changes `GroupStore.Root` at once, while panes can still hold groups from the old profile. The store records which folder its list was read from. `Reload` drops the list at once when that folder changed, and keeps it for a reload of the same folder. A scan publishes only if the root is unchanged when it finishes, and every edit method refuses a group, tab, or pin outside the current root. A new edit method must call `StaleGroup` for a group and `Stale` for a tab or pin first, and an edit made outside the store must check `IsCurrent`. A pane's UI handlers never call a mutator directly; they post it through `GroupStore.PostEdit`, which captures the root on the caller's thread and refuses the posted edit the same way if a profile switch changed it before the worker runs it. See #68 and #75. The new-tab selection after Add tab (#253) is a request keyed by the tab's folder. `RequestSelect` records it only while the folder is under the current root, and `Publish` commits it only for a scan that is kept, so a profile switch can neither select a tab in the wrong profile nor leave a request behind; an unanswered request expires after 10 seconds. |
| Pane lifetime | A pane hosted in an `HwndSource` never raises `Unloaded`, so every host calls `SidebarControl.Detach`, which detaches each section. A section's `Detach` is final: `Wire`, `Build`, and every callback it queues on the dispatcher check it, because a rebuild queued before the pane closed used to subscribe the section to static events again. A new section with subscriptions needs the same flag and a line in `DetachSections`. See #69. |
| Saving settings | `SettingsStore.Save()` normalizes and serializes `Current` on the calling thread, raises `Changed` there, and returns before `settings.json` is written. The write runs on its own lane, `WorkQueue.PostSettingsWrite`, and saves that arrive while a write is pending collapse into one write of the newest bytes. Anything that reads `settings.json` from disk must call `Flush()` first, as `ExportTo`, `OnExit`, and `OnSessionEnding` do. Never call `Flush()` from a job on the settings lane, which would wait for itself, and never post the write yourself. `Load()` writes the defaults inline, because pin mode's short-lived store is never flushed. The `SettingsStore(dir)` test constructor writes inline; use `SettingsStore(dir, post, onError)` to test the queued path. See #163. |
| Settings search targets | Every search entry's card id must have a focus target on its page, or choosing the result opens the page and focuses nothing. `Card` and `Expander` register their own; a control placed with `ChildRow`, or built outside a card, needs `cards.Register(id, control)`. `Page_EverySearchEntryCardId_RegistersAFocusTarget` fails when one is missing. See #164. |
| Dead host windows | WPF's text-input hook walks `GetParent` up from every text box on each `EVENT_SYSTEM_MOVESIZEEND` on the desktop, and throws, outside the dispatcher's handler, on a destroyed handle. That ends the process. `StaleSourceGuard` releases a pane's content when its window chain reaches a dead handle: on any window's `EVENT_OBJECT_DESTROY`, on `MOVESIZESTART`, on `WM_ENTERSIZEMOVE` in PowerPane's own windows (the shared hook skips this process), and once a second at Render priority. Pane teardown calls `StaleSourceGuard.ReleaseContent` before any call into the host's process. Two hooks for the same event run in an undocumented order, so none of this closes the race completely. See #148 and #159. |
| Move loops | To know whether a window is still being moved or sized, ask its thread: `GetGUIThreadInfo` sets `GUI_INMOVESIZE` for the whole loop. Never read the left mouse button, which is up during a keyboard move (Alt+Space) and swapped for some users. `FollowerPane.MoveSizeLoopActive` does this. See #161. |
| Logging | `Log` keeps one handle per log file open through `AppendOnlyFile`, with append-only rights, and checks every 30 seconds that the name still points at the same file, because every PowerPane process rolls the logs when it starts. Write logs only through `Log`. See #46. |
| Caches | A cache keyed by path should be an `LruCache` with a cap, guarded by the owner's lock. PowerPane runs for days, so an uncapped dictionary only grows. See #47 and #48. |
| Pin shortcuts | A pin shortcut (#299) belongs to the folder a pin points at, not to the shortcut file, because every reorder renames the files and a drag moves them. The list lives on the active `Profile` in `settings.json` as `pinHotkeys`, compared with `PinPickerModel.PathKey`, and `PinHotkeyModel` holds every rule. Edit path is the one edit that changes a pin's folder, so `GroupSection.MovePinShortcut` moves the key there, unless another pin still points at the old folder. The keys are spelled `ctrl+alt+D3`, never `ctrl+alt+3`: `HotkeyService.TryParse` reads a bare digit as a numeric `Key` value, which is not the digit key. `PinHotkeyService` registers them on one message window, ids `0xB20` upward, and `App.ApplyHotkeys` re-applies them after every save, which includes a profile switch; it records the refused numbers in `App.PinHotkeysRefused` for the Keyboard page. A press reads the window in front and sends it through `QuickSwitcher.SendFolder`, which the switcher also uses, so the two cannot drift. A key whose folder is no longer pinned does nothing and stays listed. Ctrl+Alt is AltGr on some layouts, which is why the feature is off by default and the prefix can change. |
| Selection actions | `ExplorerNavigator.GetSelectedPaths` reads the active tab's `Document.SelectedItems`, off the UI thread, only when a row is clicked. Nothing watches the selection, so a row cannot grey itself out, and says "Nothing selected" instead. The folder copy rows with a per-item form (`QuickActionLibrary.SelectionCopyId`) use the selection when there is one and the folder otherwise, through `QuickActionRunner.RunInWindow`, which the pane row and the quick switcher share. Explorer selects the folder you came from when you go up a level or back to a parent, so a copy row would copy that subfolder after an ordinary navigation. `WindowFolderHistory` keeps each window's last six distinct folders, and `IsUpSelection` treats one selected folder directly inside the current one as no selection only when the newest recorded navigation is to the current folder and the one before it was that folder or inside it. Only the latest move counts because the history is per window: matching any recent folder dropped a deliberate selection of a folder another tab had visited. Going up in one tab after navigating in another is therefore not caught, and Copy path copies the selection. The history must see every navigation: `RecentTracker`'s two-second poll missed a quick visit into a subfolder and back, so `NavigationListener` subscribes to each Explorer tab's `NavigateComplete2` and records every folder as it opens. It runs on its own MTA thread, because the events arrive on COM worker threads with no message pump to wait for, and an STA sink stalled a navigation started from the same thread. A tab's handle cannot be read from there, so the history is per window, which is why it is six deep: a tab left in a subfolder must survive moves in another tab of the same window. A copy click also records the folder. The sink types are public and `[ComVisible(true)]` because the assembly is not COM-visible. If PowerPane is killed, Explorer keeps the dead subscription and navigates as fast as before. The explicit selection rows never fall back to the folder. More than `MaxSelectedItems` is refused rather than shortened. A failed read is `SelectionReadStatus.Failed`, never an empty list, because a custom command falls back to the folder when nothing is selected, and a failed read must not point a command meant for one file at the whole folder. See #191 and #196. |
| Custom commands | `CustomCommandTemplate` splits a template into a program and arguments before any value goes in, and quotes each finished argument, so a folder name can never add an argument or end one. Quoting cannot protect a program that reads its arguments as code, so `ShellRefusal` refuses a placeholder for `cmd`, a batch file, PowerShell without `-File`, a shell given `-c`, `wsl`, and `wt`. The refusal reads the program after environment variables expand, because `%COMSPEC%` as typed looks like an unknown program. A bare name can turn out to be a batch file or a shell only once PATH answers, so `Build` runs the refusal again on the resolved program. A batch file with no placeholder is allowed and does start, as a sandbox check confirmed, because every word of its command line is the user's own. `ResolveProgram` returns a full path because CreateProcess given a bare name also searches the current directory, which would let a program planted in the folder run. A restored backup turns every command off, because a settings file may come from someone else. See #190. |
| Quick actions | A new built-in action passes `defaultEnabled: false`. Only the original ten default to on, and `EveryActionAddedAfterTheOriginalTen_DefaultsToOff` enforces that, because `NormalizeQuickActions` would otherwise add every new action to the pane of everyone already using the section. See #189. The built-in action library, path-format helpers, the quoting helper, and the unique-naming helpers all live in `PowerPane/Services/QuickActionLibrary.cs`; `QuickActionRunner` is what actually runs one against a folder. Every action that starts a process goes through `ProcessStartInfo` with its own argument list and `QuickActionLibrary.QuoteArgument`, never through `cmd /c`, because cmd.exe's own metacharacters (`&`, `^`, `%`) are not what that quoting guards against. VS Code's PATH entry is `code.cmd`, a batch file, and starting one hands its arguments to cmd.exe, so `QuickActionLibrary.FindCodeExe` walks from it to the real `Code.exe` beside its install root instead of invoking the shim at all. The PowerShell fallback for "Open in Terminal" needs a second, different quoting rule of its own (`QuickActionLibrary.TerminalArguments`): PowerShell's `-Command` parses the rest of the line as script text, so a folder name containing `$` needs PowerShell's single-quoted string literal, not `QuoteArgument`'s CommandLineToArgvW-style quoting. The pane's Quick actions section resolves "the folder the host Explorer window shows" fresh at the moment of each click, through `ExplorerNavigator.GetCurrentPath(SidebarControl.HostWindow)` posted to `WorkQueue`, rather than caching it at build time, because the pane does not rebuild on an Explorer navigation. The section is hidden entirely (not merely built empty) inside a file dialog or on the desktop dock, neither of which has an answer for that. |
| Explorer Show toggles | `ExplorerViewOptions` flips Explorer's View > Show options, which are per-user and shared by every Explorer window. Hidden items, extensions and item check boxes go through `SHGetSetSettings`, which writes the registry and changes open windows at once. Compact view has no such call: writing `UseCompactMode` and broadcasting a `ShellState` setting change changes open windows at once. The navigation pane is byte 4 of `Modules\GlobalSettings\Sizer\PageSpaceControlSizer`, which a window reads only when it opens a different folder; a refresh, F5, or reopening the same folder does not apply it. All of this was measured in Windows Sandbox. Tests never read or write these values, because they would change the settings of whoever runs them. A row's check box is re-read after a toggle, on a General `UserPreferenceChanged`, and when the pointer enters the section, because nothing else tells PowerPane about a change made from Explorer's own menu. |
| Add to PowerPane verb and queue | The verb's registry key name must stay `PowerPanePin` in all four places (`Directory`, `Directory\Background`, `*`, and `Drive`) in `Installer.iss`, `Install.ps1`, and `Uninstall.ps1`: Inno Setup does not remove a renamed key on upgrade, so a new name would leave the old entry beside the new one. `scripts/check-rules.ps1` fails when the three files name different keys. The visible text is "Add to PowerPane", while the pane's own items are still pins. Explorer may start the verb once per selected item, in separate processes, and the behavior for a multi-selection is not verified. Every launch therefore writes its paths into `%LOCALAPPDATA%\PowerPane\PinQueue` through `PinQueue` (one file per path, written under a `.tmp` name and renamed), then tries to claim the named mutex `PinQueue.PickerMutexName`. The launch that wins waits until no file has arrived for 400 ms (or 3 seconds in all), drains the queue, and shows one `GroupPickerWindow`. The other launches exit at once. While the window is open the owner drains every 500 ms and adds late arrivals to it, and after the window closes it releases the mutex and checks the queue once more, so a launch that lost the race during close gets a second picker. A queue file older than 10 minutes is deleted unread. Never use `CrashGuard.InstanceMutexName` here, because pin mode must not touch the tray's single-instance check. The picker is placed by `PickerPlacement.Place` in device pixels against the work area and scale of the monitor under the pointer (`NativeMethods.MonitorAtPoint`), and again on every size or scale change. `GroupStore.AddPins` turns an implicit tab into a numbered subfolder, so `PinMemory` is saved from the rescanned tab and not from the object used to pin. The picker skips an item whose path is already the target of a pin in the chosen existing tab (#252). `PinPickerModel.PathKey` ignores case, reads `/` as `\`, and drops trailing separators; it does not resolve short names, links, or environment variables, so such a duplicate is still added. The check reads the tab as it was when the picker opened, so a pin added elsewhere while it is open is not seen. |
| Dock display picker | `PowerPane/Explorer/MonitorPicker.cs` lists connected monitors for the Pane page's Display row and resolves the stored choice to one of them; `AppBarHost` reads `AppSettings.DesktopDockDisplay` live (the same way it already reads `SidebarWidthPx`) rather than taking it through its constructor, so a display change repositions the dock through the existing settings-changed path with no restart. `MONITORINFOEX.szDevice` ("\\.\DISPLAY2") is only a label: it can renumber across a reboot or a display change, so the stored id is the monitor's own device-interface path from `EnumDisplayDevices(..., EDD_GET_DEVICE_INTERFACE_NAME)` instead. An id that is not connected, or is null/empty (the "Primary display" default), resolves to the live OS primary, never to a fixed monitor that might also be gone; `MonitorPicker.ResolveMonitor` is the pure decision, tested with invented monitor lists. `AppBarHost` reserves against the monitor's full bounds in reserved mode and its work area in auto-hide mode, both taken from the resolved `MonitorDescriptor`, and tracks the last resolved monitor's id so a change of monitor (a different choice, or a fallback to/from primary) forces a fresh `ABM_SETPOS` even where the #145 same-rect guard would otherwise have skipped it. `WM_DISPLAYCHANGE` on the dock window re-runs the same positioning on a monitor connect, disconnect, rearrange, or resolution change. See #146. The same-rect guard skips only `ABM_SETPOS`, never the move: `AppBarHost.NextReserveStep` still moves the window back when its own rectangle no longer matches the reservation, because a scale change resizes the window (WPF keeps its DIP size) while the reservation in physical pixels stays the same. The window's `DpiChanged` event re-runs the positioning at Background priority, after WPF has applied its suggested rectangle. See #160. Since #177 the auto-hide dock can be 80, 60 or 40 % of the work area tall, centred: `AppBarHost.DockBand` computes the band, never under 320 DIP, and `AutoHideRect` puts the collapsed trigger strip on the same band, so the pointer finds it where the dock opens. Reserved mode ignores the height, because the shell shrinks the work area by the strip's full width over the display's whole height whatever the strip's own height. |
| Settings reorder drag | `ReorderDrag` uses mouse capture, never `DragDrop.DoDragDrop`, because `DoDragDrop` runs a nested message loop on a UI thread that shares Explorer's input queue in inside mode. A drop and the Move buttons go through the same `MoveSectionTo` or `MoveActionTo`, which is where the order logic is tested. The grip is a `Border`, which has no UI Automation peer, so a Sandbox job finds a row through its "Move ... up" button. |
| Settings info button | `SettingsCards.InfoButton` holds a row's description in a tooltip. Use it only for supplemental text, because Microsoft's guidance is that essential information belongs on screen. That is why a custom command keeps its template on its row: the template says what the row will run. A tooltip alone reaches a mouse user only, so the button is a tab stop, opens on keyboard focus and on a press, and closes on Escape. `SectionsPage.Describe` states when a section does not appear, and its conditions must match `SidebarControl.BuildSection`. See #205. |
| Dock edge and shared edges | `AppSettings.DesktopDockEdge` ("right", or null for left) is read live by `AppBarHost`, like the display choice, so a change repositions the dock through the settings-changed path with no restart. Both positioning paths also apply the edge to the sidebar, because a right-edge dock needs its width grip on its left side, a flipped drag direction, and a mirrored title chevron (#184). `SetReservedPosition` tracks the last edge beside the last monitor id and clears `_haveReserved` when it changes, so the next `ABM_SETPOS` (with the new `uEdge`) replaces the old reservation even if the rectangle looks unchanged. `ProposedStrip(monitor, width, right)` must stay a pure function of monitor, width, and edge (#145). After `ABM_QUERYPOS` the shell trims only the side facing the anchored edge (Right for the left edge, Left for the right edge), so `AdjustQueriedStrip` re-derives the far side from the width; fixing Right on a right-edge strip would leave a wrong-width strip in the wrong place. In auto-hide mode on an edge that another display touches (`AppBarHost.IsEdgeShared`, over the `MonitorPicker` list), the pointer crossing to that display passes through the 4 px trigger strip, so `MouseEnter` starts a 300 ms dwell timer instead of expanding, `MouseLeave` cancels it, and the tick expands only if the cursor is still over the window. An outer edge still expands at once. The collapsed trigger keeps its 46 px dead corners on both edges (`AutoHideRect`): top-right is a maximized window's close button, bottom-right is the clock area. Windows reserves appbar space per monitor, so reserved mode on an inner edge needs no special code. See #177. A maximized window's rectangle reaches past the work area by an invisible frame, and a reserved dock is not topmost, so that frame lies over the dock's inner edge and takes its clicks. `GetSystemMetricsForDpi` reports the frame as at most 8 DIP at every scale from 100 % to 350 %, so a reserved dock's grip is `SidebarControl.ReservedDockGripWidth` (14 DIP), which leaves the usual 6 DIP clear. Making the dock topmost would also solve this, but it would then have to step aside for full-screen apps through `ABN_FULLSCREENAPP`. See #185. |

The trace provider's GUID in `scripts/trace/PowerPane.wprp` is derived from `PerfTrace`'s `EventSource` name, and `PerfTraceTests` fails when they drift. The literal "QuickPane" survives in exactly three places on purpose: the installer's and `Install.ps1`'s check for the old install, and `AppSettings.FormerDataFolderName`, which `AppSettings.MapFormerDataPath` and `UiState.MapFormerKey` use. |

## The original project

Explorer PowerPane began as a fork of `lso2/QuickPane` and was renamed in 4.0.0.0. Changes no longer flow between the two, so a clone needs no `upstream` remote. These things stay as written, because they credit the original or record history: `LICENSE` with its original copyright notice, the About page's Licence card, which says PowerPane began as a fork of QuickPane by lso2 (PlexPixel), and its "Support QuickPane's author" link, whose description names QuickPane's creator (#273), the README's Author section, and citations of `lso2/QuickPane` issues. The support link is the About page's only link outside this repository, and the pane carries no donation link for anyone (#18, #266). QuickPane is GPL-3.0 since 2026-11-14, so no code from its later versions may be copied into PowerPane, which stays MIT. `CHANGELOG.md` entries and `docs/releases/` documents before 4.0.0.0 also keep the QuickPane name.

## Releasing

1. Choose the version with Semantic Versioning, which releases use from 4.1.0: raise the patch number for fixes only, the minor number when something is added and existing use still works, and the major number when existing use breaks. The release tag is `v<major>.<minor>.<patch>`, such as v4.1.0. Set `PowerPane/Properties/AssemblyInfo.cs` (both attributes) to the same three numbers followed by `.0`, such as 4.1.0.0, because Windows requires four parts. `scripts/release-version.ps1` holds this mapping, and the release workflow, the winget workflow, and `scripts/package.ps1` all use it. Releases up to 4.0.0.1 had four-part tags, which still map to themselves.
2. Add a `CHANGELOG.md` entry with Added, Changed, and Fixed sections, linking issues. When a release needs more than its changelog section, write a full release document in `docs/releases/<version>.md`, as for 3.10.0.2, the first published release, and 4.0.0.0, the rename. Also update `PowerPane/Services/WhatsNew.cs`, which is the short summary on the About page. Set its `Version` to the new version and rewrite its lines. `WhatsNewTests` fails until its version matches the assembly's, so the tests catch a forgotten update. The "At a glance" table in a release document is a good source for these lines.
3. When the release changes what a user sees, add an item to "What changed since QuickPane" at the top of `README.md`. Link it to the release that will publish it, and to its issues. A version that is never published gets a line under its `CHANGELOG.md` heading naming the release that first shipped its changes.
4. Merge to `main` through a pull request with green CI.
5. Tag the merged commit on `main` and push the tag: `git tag -a v<version> -m "PowerPane <version>"`, then `git push origin v<version>`.
6. The `release` workflow then runs on that exact commit. It refuses a tag that `scripts/release-version.ps1` does not accept, a tagged commit that is not on `main`, and an exe whose version is not the one the tag maps to. It builds, tests, packages, and attests the files' provenance. Then it creates a **draft** release for the tag with the installer, the zip, and `SHA256SUMS.txt`. The installer is attached twice: as `PowerPane-<version>-x64-setup.exe`, which the `winget` workflow looks for, and as `PowerPane-x64-setup.exe`, so that `releases/latest/download/PowerPane-x64-setup.exe` always fetches the newest published installer. The workflow creates that draft, or refreshes the draft that already exists for that tag. It never touches a published release. Its run summary prints the publish command.
7. Download the installer from the draft, run it over an existing install on a real desktop, and test it. Then publish the draft: `gh release edit v<version> --draft=false -R prisant-labs/windows-explorer-powerpane`. Publish it as a full release, not a pre-release. The in-app update check reads `releases/latest`, which never returns drafts or pre-releases.
8. Publishing starts the `winget` workflow, which opens a pull request in `microsoft/winget-pkgs` for the new version of `PrisantLabs.PowerPane`, using Microsoft's `wingetcreate` from a pinned release whose hash it checks. It needs the repository secret `WINGET_TOKEN`, a personal access token with `public_repo` scope, and skips with a notice without it. A winget maintainer merges the pull request, usually within a day or two. To retry one version, run the workflow by hand with its tag.

If the desktop test fails, fix the bug on `main`. Then bump the version, and tag again. Do not move a pushed tag. To try the workflow without releasing anything, run it by hand from the Actions tab: a run that no tag started builds, tests, and packages, keeps the files as an artifact, and creates no release.

Anyone can check that a download was built by this workflow from this repository: `gh attestation verify PowerPane-<version>-x64.zip -R prisant-labs/windows-explorer-powerpane`.

The binaries are not code-signed. The installer's `AppId` is PowerPane's own since 4.0.0.0, so it upgrades an existing PowerPane install and its Add/Remove Programs entry in place, and it refuses to install while QuickPane, which used the original project's `AppId`, is still installed. Never change the `AppId` again: a new one would add a second Add/Remove Programs entry beside the old. To try a build without the installer, close PowerPane with `--exit` and replace `PowerPane.exe` in `%LOCALAPPDATA%\PowerPane`. Add/Remove Programs then keeps showing the previously installed version.
